# 需求与版本演进

本文记录使用者的实际需求、第一版后的反馈，以及当前实现保留这些决定的原因。它用于防止以后维护时把已简化的流程改回去。操作说明见 [README](../README.md)，实现细节见 [模块设计说明](DESIGN.md)。

下文按开发阶段整理为 v1.0、v1.1、v1.2；这是需求演进记录，不表示 GitHub 已创建对应标签或发行包。当前代码版本为 1.2.0。

## 1. 最初要解决的问题

使用者希望为量产小车建立一份统一台账：

- PCBA、结构件备了多少，每一套在哪里；开发和采购花了多少钱。
- 购买截图、发票等凭证能跟随账目保存，也能记录实际收入。
- 一家店收到哪几台车，每辆车的车架号与 PCBA 号是什么。
- 门店路由器、远程控制账号等信息可随时查阅。
- 安装图、地图参数、安全池参数及其他文件能按门店归档。

最终目标中有云平台，但本阶段先做本机可录入、可保存、可查询的版本，独立于现有小车调试程序，桌面双击打开。用户先试用，再集中修改，逐步确定真正需要的字段和操作。

## 2. 第一版前确认的业务规则

| 确认项 | 决定及原因 |
| --- | --- |
| 逐套管理 | PCBA 与结构件都记录独立编号，结构件编号就是车架号，不能只存总数量 |
| 编号格式 | 不强制格式、保留前导零，同类型不可重复，适应现有生产编号 |
| 扫码操作 | 扫描或搜索后进入清单，由人最后确认，避免扫到即扣库存 |
| 分别出库 | PCBA、结构件可能在不同时间领用，之后再组成车辆 |
| 两种出库用途 | 装车领用和门店备件分别记录，不能都当作已经成车 |
| 整车出货 | 车辆已配对才可出货；配件先前已经出库，整车出货不能再次扣减 |
| 换板与转店 | 保留旧板、新板、原因和门店变化；旧板去向必须明确 |
| 安装资料 | 第一版归档文件与说明，不解析地图或安全池；同项更新替换文件 |
| 收支 | 实际付款才算支出，采购与付款不能重复累计，不计算应收应付 |
| 密码与恢复 | 正式台账解锁后访问，账号加密，提供单独保存的恢复密钥 |
| 演示与正式 | 演示方便试操作，正式从空台账开始，两者数据隔离 |
| 更正 | 普通资料可编辑，完成的库存与出货操作通过撤销或后续业务留痕 |

这些规则解释了为什么“领用待装车”“门店备件”“换板去向”和历史记录是必要部分，不能在简化表单时一并删掉。

## 3. v1.0：先走通完整业务

第一版提供总览、收支、采购与库存、车辆、出货、门店、设置与备份，建立本地服务、数据库、附件和账号加密能力。

当时表单较完整：收支包含往来方、关联门店、采购批次与用途事由；采购包含供应商、金额等；门店账号按名称、用户名、密码、地址和备注分项填写。

试用后，使用者明确希望收支和入库更轻量、附件查看更直接、门店账号可以自由组织。后续改动围绕这些反馈进行，并保留必要的数据兼容和追溯规则。

## 4. v1.1：减少录入负担，钱和库存分开

### 4.1 分类改为选择项

**用户反馈：** 选好收入或支出后，分类不应手工打字，应直接给选项。

**当前结果：**

| 方向 | 分类 |
| --- | --- |
| 收入 | 甲方回款 |
| 支出 | PCBA采购、结构件采购、研发耗材、吃饭、差旅、出货耗材 |

**设计原因：** 常用类别数量少，选择比手输更快，也能避免同一类别写成不同名称而难以筛选。分类随方向切换，后端也校验；旧记录的历史分类保留兼容。未来需要新类别再扩展，不要求用户每次现编分类。

### 4.2 收支只留一处备注

**用户反馈：** 删掉往来方、关联门店、采购批次、用途事由，保留备注。

**当前结果：** 新建收支只需要方向、分类、金额、日期、备注和附件。旧字段不再出现在当前录入流程，历史数据仍保留。

**设计原因：** 这份台账主要用于日常记账，不要求每笔交易建立复杂关联。背景可以统一写在备注，避免重复填写和选择无关项目。维护时不能因为数据库还有旧字段，就默认应把它们重新放回表单。

### 4.3 收入红色、支出淡绿色

**用户反馈：** 收支账本里用不同颜色区分，收入红色，支出淡绿色。

**当前结果：** 收支汇总、金额和方向标识使用对应颜色，并保留文字与正负号帮助识别。

**设计原因：** 遵循使用者的识别习惯。不要在后续换主题时无意改成另一套颜色约定。

### 4.4 附件支持粘贴、拖入和预览

**用户反馈：** 购买截图或发票可直接粘贴照片、拖动文件导入，图片或 PDF 鼠标悬停预览。

**当前结果：** 保留选文件，同时支持 Ctrl+V 粘贴图片与文件拖入；待上传清单可预览和移除；图片与 PDF 提供浮层预览，其他文件下载。

**设计原因：** 截图常来自剪贴板，发票常来自下载文件；分别适配实际来源，减少先另存图片再选文件的步骤。预览应紧贴用户正在看凭证的位置。

**后续澄清：** 仅详情附件列表能悬停仍不够，v1.2 又把预览接到收支主列表的附件数量位置，见下文。

### 4.5 “采购入库”改为“入库”，删除金额与供应商

**用户反馈：** 本批采购金额在收支中已记录，库存不需要重复填写；“采购入库”改成“入库”；供应商等字段也删除。

**当前结果：** 入库只处理日期、编号、数量与备注，不要求采购金额或供应商，不自动生成付款支出。界面名称同步简化，后续再拆分两种配件的入口。

**设计原因：** 收支回答钱的流动，库存回答实物的状态。两个模块各负责一件事，既减轻操作，也避免重复统计。批次分组继续用于追溯，不再被当作采购成本账。

## 5. v1.2：按使用者截图补齐交互

### 5.1 点击左侧空白关闭右侧详情

**用户反馈：** 右侧框打开后，点击左边空白应能关闭，不应必须找关闭按钮。

**当前结果：** 点击详情抽屉左侧遮罩即可关闭；保留关闭按钮。表单和预览浮层内部操作不应误触关闭。

**设计原因：** 查看详情是临时动作，点击外部回到列表符合日常操作预期。涉及未保存自由文档时仍提示，避免降低关闭成本的同时丢失输入。

### 5.2 收支主列表直接悬停附件数量

**用户反馈：** “悬浮预览”指截图中的收支主页面，鼠标放在附件位置就主动打开。

**当前结果：** 主列表的“附件 N 份”可直接悬停预览，不需要先打开账目详情；多附件可切换，PDF 可翻页，详情内的预览也保留。

**设计原因：** 核对一笔金额时，凭证就在同一行，少一次进入详情和退出详情。预览必须严格对应当前行，不能因切换记录、异步加载或层级关系显示另一笔附件。

### 5.3 入库入口也分成两种

**用户反馈：** PCBA 出库和结构件出库都独立，入库也直接做成 PCBA 入库、结构件入库。

**当前结果：** 总览快捷入口和库存页面分别提供两种入库，进入后固定对应类型。

**设计原因：** 入库与出库保持一致的操作方式，减少每次选择类型，也减少批量扫码后才发现选错类型的风险。

### 5.4 只有账号备忘改为自由文档

**用户反馈：** 门店资料希望能像空白文档一样自由填写。进一步确认的范围是：**只把账号备忘改成自由文档，联系人、电话、地址等字段保留。**

**当前结果：** 门店基础资料、车辆和附件继续单独管理；账号备忘改为一店一份加密自由文档，可以自行排版记录多个账号、密码和操作说明。旧版账号首次打开时可整理带入，保存后以文档为准。

**设计原因：** 不同门店的路由器、远程工具和参数形式不同，固定用户名、密码、地址等表单未必适合全部情况。自由文档保留表达空间，加密要求继续保留。这个决定不等于把所有门店信息都塞进文档。

### 5.5 门店编码由用户填写

**用户反馈：** 截图中的 `STORE 01` 应允许用户填写编码，以后要对接另一套云平台。

**当前结果：** 门店编码可以新增和编辑，非空编码不可重复，保留大小写与前导零；不再使用列表顺序作为门店编码。内部关联继续使用稳定 ID。

**设计原因：** 外部平台的业务编码可能由用户或对方平台规定，不能由本地列表排序决定。修改编码不能让车辆、附件和历史失去归属。当前只预留编码能力，没有实现外部云平台连接。

## 6. 为上述体验补齐的可靠性处理

下面是实现这些需求时配套完成的处理，用于说明边界，不作为额外的用户需求。

| 场景 | 当前处理与原因 |
| --- | --- |
| 内嵌 PDF 在部分浏览器显示空白 | 使用本地 PDF.js canvas 渲染，不依赖浏览器内嵌 PDF 插件 |
| 账目保存成功、附件失败后重试 | 复用已保存账目 ID 与上传请求，避免重复记一笔钱 |
| 文件同名、同大小但内容不同 | 不仅凭文件名和大小去重，避免丢失不同凭证 |
| 扩展名伪装成图片或 PDF | 根据实际文件头判断预览类型，其他文件下载 |
| 安装资料替换失败 | 先保存新文件，再切换引用；失败时保留原文件 |
| 旧用途在清空备注后重新出现 | 记录备注已编辑状态，尊重用户最新输入 |
| 自由文档未保存就关闭或刷新 | 提示未保存；锁定时清除敏感界面，不把正文缓存到浏览器存储 |
| 大量中文或需转义的字符 | 文档上限 40000 字符，并校验加密负载可承受的体积 |
| 普通账号接口误操作自由文档 | 使用保留标识和专用接口，验证文档确实属于指定门店 |
| 同时开两个窗口或重复点击 | 状态检查、数据库约束、事务和幂等请求共同防重复出库 |
| 损坏备份或切换失败 | 隔离校验后再替换，失败回滚，正式恢复后重新解锁 |

## 7. 后续维护时应保留的决定

1. **先少填、再扩展。** 当前删去的表单字段是试用后的明确选择，不是忘了做。
2. **收支只记钱，库存只管物。** 不能为了“自动化”重新把入库直接计为支出。
3. **每套实物与每辆车仍可追溯。** 简化页面不能破坏编号唯一、绑定关系和历史。
4. **附件在列表就能查。** 不要把主列表悬停预览退回为只能进入详情后点击查看。
5. **自由文档限于账号备忘。** 联系人等字段、车辆与安装资料继续独立保存。
6. **业务编码可以编辑，内部 ID 保持稳定。** 对接其他平台时使用明确映射，不使用显示顺序。
7. **本地与云端分阶段。** 当前 GitHub 用于源码管理；未来联网同步、共享访问和权限需要另行设计，不能直接将本机端口开放为云服务。

新增需求时建议继续记录“用户遇到了什么、最后决定怎么做、为何这样做、现有数据如何兼容”，并同步更新 README 的实际操作方法。
